# BYOT 1.0.35 — Pairing messages and live updates that come back

No new TestFlight feedback has arrived since 2026-10-06; all 72 items are recorded in earlier releases. This release instead takes its polish from the anomalyco/opencode issues filed by people on OpenCode's own iPhone TestFlight app and by people using OpenCode's web UI from a phone. It builds on the 1.0.34 source (`6e42a68`, `feat/opencode-pairing`).

## What changed

| Area | Change | Source |
| --- | --- | --- |
| Pairing, loopback addresses (`OpenCodeOneTimePairing.swift`) | On a phone, `127.0.0.0/8`, `::1` and `localhost` addresses in an OpenCode 2 code are dropped, because they point at the phone. A code with nothing else, such as a pasted `http://127.0.0.1:…/auth/connect/…` link, now says so and suggests `opencode pair --remote` or `opencode service set hostname 0.0.0.0`. Before, byot tried the phone's own loopback and then asked whether the computer was awake; `http://localhost` links were refused as "must use a local network IP address". The simulator and the iPad app on a Mac keep these addresses, since they share the computer's loopback. | [#54871](https://github.com/anomalyco/opencode/issues/54871): 2.0.27 put `127.0.0.1` in the QR code; the printed links still start with it |
| Pairing, relay outages (`OpenCodeServerSetupViews.swift`) | When every address is an `opentunnel.xyz` relay and none answers, byot says the relay is the problem and suggests `opencode service restart`, then a new `opencode pair --remote`, which is OpenCode's own advice. Before, it suggested running `opencode pair --remote`, which the person had just done. | [#54627](https://github.com/anomalyco/opencode/issues/54627) (the official iOS app's "Couldn't reach the OpenCode server"), [#54596](https://github.com/anomalyco/opencode/issues/54596), [#55873](https://github.com/anomalyco/opencode/issues/55873) |
| Live updates, silent drops (`OpenCodeTransport.swift`, `OpenCodeEventStream.swift`) | Event streams had a 24-hour request timeout, so a connection that died without closing (the computer slept, the phone changed networks) left a conversation or the session list quiet but still showing as live. OpenCode 1 sends a `server.heartbeat` event every 10 s and OpenCode 2 a `: heartbeat` comment every 15 s (upstream `packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts` at v1.18.29, `packages/server/src/handlers/event.ts` on dev). Once a stream has sent one, 45 s of silence cancels it with "The connection to OpenCode went silent.", and the existing reconnect and reconciliation take over. A stream that never sends a heartbeat is left alone. | [#55673](https://github.com/anomalyco/opencode/issues/55673): the web UI stays broken after a network switch on an iPhone |
| Live updates, return to the app (`OpenCodeSessionStore.swift`) | A conversation whose stream dropped while byot was in the background reconnected only after its backoff, which grows to 15 s. Returning to the app now reconnects at once when the stream is down. A stream that is still live is left open. The session list already restarted its stream on return. | same |
| Strings | Three new strings, each with Simplified Chinese. | |
| Telemetry | The stall reports as the existing `event_stream` error class; the event schema is unchanged. | |

## Considered and left out

- [#55549](https://github.com/anomalyco/opencode/issues/55549) (on a phone, Return sends and no new line can be typed). byot's message field is set to send on Return (`.submitLabel(.send)`, `.onSubmit(send)`). Whether Return should add a line instead is a product decision, so this build leaves the field unchanged.
- [#54279](https://github.com/anomalyco/opencode/issues/54279) (slash commands missing before the first message) is about the web app's draft page. byot's own command list was not checked.

## Validation

Unit tests ran on the Mac mini in a fresh build of this source, on the iPhone 17 simulator "BYOT Feedback QA" (iOS 26.5, Xcode 26.5, 17F42).

| Run | Result |
| --- | --- |

| Control: the heartbeat arming and the foreground reconnect commented out | The three tests for the fixes failed: both stall tests ran to the stub's 5 s safety close, and the reconnect missed its 500 ms window. The two guard tests passed. |
| Whole `BYOTTests` target | _pending_ |

## Not covered

- No real network switch or computer sleep was exercised; the stall is covered with a stubbed stream that sends heartbeats and then goes silent. The owner's phone is the check: open a running conversation, switch Wi-Fi to mobile data, and expect the "Reconnecting" note within about a minute, then the reply.
- The relay message was checked by unit test only; the relay itself was up.
