# BYOT 1.0.38 — Current `main` to TestFlight and App Store review

No new TestFlight feedback has arrived since the 1.0.36 item; all earlier items are recorded in previous releases. This release carries `main` as it stands (`6eaea56`) to the App Store, which has been on 1.0.35 since 2026-10-19.

## Why 1.0.38 and not 1.0.37

TestFlight already holds a build labelled 1.0.37 (`20261027124118`, uploaded 2026-10-27) that was archived from the local branch `codex/testflight-feedback-20261027` at `60b88f8`. That commit was never pushed or merged, so nothing on `origin` corresponds to the build internal testers have been using. Reusing 1.0.37 would put two different sources behind one version number, so this release takes the next free number instead. `docs/releases/1.0.37.md` exists only on that branch.

## What changed since the live 1.0.35

The App Store build of 1.0.35 was archived from `390a78e`. Against that commit, `main` changes five source files:

| Area | Change |
| --- | --- |
| Session list rows (`OpenCodeProjectSessionsView.swift`, `OpenCodeConnectedView.swift`, `OpenCodeSessionBrowserStore.swift`) | Rows said "Status unavailable" whenever a project had no status map, which covered a saved list shown at launch while byot reaches the server, a project still loading, and a server that answered with an error. A sleeping tailnet computer can hold the first request for URLSession's default 60 s, so for up to a minute every row read "Status unavailable". Rows now say "Connecting" until the project answers, show no status at all while the offline notice is up, and keep "Status unavailable" for a server that answered with an error. Shipped to TestFlight as 1.0.36; never released. |
| Usage data (`BYOTTelemetry.swift`, `BYOTTelemetryOpenCode.swift`) | URLSession throws `URLError(.cancelled)`, not `CancellationError`, so every in-flight project fetch cancelled by the app going inactive or the list leaving the screen was recorded as `error_occurred(network, session_list)` — up to three per cancellation. Cancelled loads are now classified as cancelled and not reported. Separately, a server negotiated before the person answered the usage-data question was marked reported even though the event was dropped, so an opt-in launch never sent `server_connected`; it is now held in memory and sent on opt-in. |
| Strings | None new. |
| `Sources/Info.plist` | Unchanged since 1.0.35, so no permission or privacy-label change. |

Internal testers have had that fix since 2026-10-27; 1.0.38 does not. Merging that branch and cutting 1.0.39 is the follow-up.
