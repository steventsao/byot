# BYOT 1.0.44 — reading a long reply while OpenCode is still writing it

Two fixes to how the transcript scrolls during a running turn. Both come from the known issue listed with [1.0.43](1.0.43.md). The build goes to TestFlight only; 1.0.43 is still waiting for App Store review.

## Why 1.0.44

1.0.43 (`20261122220226`) is waiting for review, so this build takes the next number.

## What changed since 1.0.43

| Area | Change |
| --- | --- |
| Responsiveness, `OpenCodeSessionView.swift` | Resting just above the end of a running turn several screens tall held the main thread at 100% in SwiftUI's lazy stack, and the app stopped responding until the turn was scrolled away from. The rows that follow the conversation sat in the lazy stack: the activity indicator, task progress, retry and model notices, queued prompts, pending actions and the bottom anchor. The stack built them ahead of the screen with heights estimated from the tall turn, then kept rebuilding and dropping them. They now sit in a plain stack under the lazy one; the conversation rows stay lazy. Samples taken during the hang spent their time in `LazyStack.measureEstimates`, `LazyLayoutViewCache.updateItemPhases` and `updatePrefetchPhases`, with an item-phase mutation queued after every pass. |
| Following, `OpenCodeTranscriptParts.swift`, `OpenCodeSessionView.swift` | 1.0.43 measured the distance from the end with the bottom inset where the scroll offset needs the top one. On an iPhone 17 Pro the end of the transcript read as about 270 pt away. Scrolling back to the end by hand never resumed following, and any touch-scroll at the end stopped it. The distance now uses the top inset. Only the reader's own scroll toward history stops following, and output that lands while a fling settles moves the end, not the reader. |
| Tests | `OpenCodePolishUITests.testRestingInsideARunningTurnSettles` stops at twelve places in and above the running turn, before and after "Jump to latest", and fails if the app does not come to rest within 10 s of any of them. `testLiveTurnFollowsUntilReaderScrollsBack` gets back the leg 1.0.43 left out: a swipe that stops inside the turn, then scrolling back to the end by hand. `OpenCodeTranscriptPartTests.followsUntilReaderScrollsBack` uses the measured geometry and adds a fling that ends while output arrives. |
| Strings | None added or changed. |
| `Sources/Info.plist` | Unchanged, so no permission or privacy-label change. |

## Validation

Run on the Mac mini (Xcode 26.5) on an iPhone 17 Pro simulator, iOS 26.5.

| Run | Result |
| --- | --- |
| `testRestingInsideARunningTurnSettles` on `main` (1.0.43 code) | **Failed**: stop 6, the first swipe after "Jump to latest", did not come to rest for 60.5 s. |
| The same stops with the trailing rows still in the lazy stack, across 9 diagnostic runs | Hung in all 9, always on stop 6 or 7, including runs that changed how "Jump to latest" scrolls. |
| `testRestingInsideARunningTurnSettles` with the fix | Passed 8 of 8 runs; the last 3 include the inset fix. |
| `testLiveTurnFollowsUntilReaderScrollsBack` with both fixes | Passed 3 of 3. With the layout fix but not the inset fix, it failed all 6 runs on "Scrolling back to the end should follow again". |
| `BYOTTests` with both fixes | **796 tests: 788 passed, 8 skipped (live-server tests), 0 failed**: 679 swift-testing tests in 72 suites plus 117 XCTest tests. |
| `OpenCodePolishUITests` with both fixes | 17 of 17 passed. |

## How the cause was found

- A CPU sampler on the Mini took `sample` of the app once it had held more than 90% CPU for 3 s, and a simulator screenshot at the same moment. The screenshot showed the hang begins with the end of the turn just below the screen.
- Moving the trailing rows out of the lazy stack, removing them, or making the whole transcript a plain stack each let the swipe settle. Changing how "Jump to latest" scrolls did not: animated or not, anchored or not, and iOS 18's scroll-to-edge all hung on the same stop. Neither did keeping the activity animation off screen, or dropping the bottom anchor's position report.
- The follow bug showed up once the swipe no longer hung. A log of every scroll-geometry change during the test read 270 pt at the very end.

## Not covered

- iOS 17 has no prefetching lazy stacks. It keeps the previous follow rule, which reads the bottom anchor's position, and was not run.
- The fixes were not tried on a device before this build.
- The full `BYOTUITests` target was not run.
